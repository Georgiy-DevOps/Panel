# Защита серверов

Это проверяемые конфигурации, а не универсальный установщик. До применения нужно
проверить ОС, SSH-порт, открытые службы, действующие правила и резервный доступ.
Секреты, ключи и реальные базы в этот каталог не добавляются.

## Состав

- `90-fleet-sshd.local` → `/etc/fail2ban/jail.d/90-fleet-sshd.local`: SSH на порту
  22, чтение journald, 5 ошибок за 10 минут, блокировка на час с увеличением
  повторных блокировок до 7 дней; действие nftables для IPv4 и IPv6.
- `00-fleet-hardening.conf` → `/etc/ssh/sshd_config.d/00-fleet-hardening.conf`:
  сокращение времени входа и числа попыток, запрет X11 и пустых паролей,
  подробный журнал аутентификации. TCP forwarding сохранён для рабочих туннелей.
- `52fleet-upgrades` → `/etc/apt/apt.conf.d/52fleet-upgrades`: ежедневные
  автоматические обновления с сохранением выбранных Ubuntu security-источников,
  без автоматической перезагрузки.
- `50-fleet.rules` → `/etc/audit/rules.d/50-fleet.rules`: аудит изменений
  SSH, ключей root, учётных записей, sudo, systemd и фаервола.

Пакеты: `fail2ban`, `auditd`, `unattended-upgrades`; UFW и nftables проверяются
до установки. На уже работающем сервере сначала сохранить конфигурации и
проверить доступные версии из доверенных репозиториев ОС.

## Фаервол

Если используется UFW с `iptables-nft`, nftables уже является частью действующей
схемы. Нельзя параллельно включать отдельный `nftables.service` с `flush ruleset`:
это может удалить правила UFW, Docker и Fail2ban. Не отключать управление
правилами в Docker. Публикации контейнеров проверяются отдельно от UFW: публичные
порты Docker могут проходить через цепочку FORWARD, минуя фильтрацию INPUT.
Панель должна оставаться опубликованной только на `127.0.0.1:3080` за Nginx.

## Порядок применения SSH

1. Сохранить `/etc/ssh`, `/etc/ufw`, `/etc/fail2ban` (если существует),
   `/etc/nginx`, конфигурации systemd и вывод `sshd -T`, `ufw status verbose`,
   `nft list ruleset` в каталог root с правами 700.
2. Проверить личный ключ владельца через независимую сессию Termius и наличие
   консоли восстановления провайдера. Служебный ключ автоматизации не заменяет
   личный резервный доступ владельца.
3. Перед изменениями SSH/фаервола подготовить откат к сохранённым файлам и
   отложенный запуск отката через systemd. Не заменять уже существующие файлы
   конфигурации без сравнения.
4. Проверить `sshd -t`, затем `sshd -T` с учётом `Match` для нужных пользователей.
   В OpenSSH важен первый найденный параметр, поэтому ранние include-файлы могут
   иметь приоритет над остальной конфигурацией.
5. Перечитать SSH, проверить новое подключение и HTTPS панели. Только после этого
   отменить таймер отката.
6. Отключать парольную аутентификацию и прямой root-вход отдельным шагом после
   проверки личного входа администратора с sudo. Эти шаблоны сами этого не делают.

Не менять SSH-порт или socket activation без отдельной проверки: сервер может
использовать `ssh.socket`, а не только `ssh.service`.

## Проверки

```sh
sshd -t
fail2ban-client -t
fail2ban-client status sshd
auditctl -l
ufw status verbose
docker ps --format '{{.Names}} {{.Ports}}'
systemctl is-active fail2ban auditd
```

Нужно проверить реальное создание и снятие блокировки в nftables, а не только
статус процесса Fail2ban. Для локальной проверки действия можно использовать
не маршрутизируемые в интернете адреса документации `198.51.100.254` и
`2001:db8::f00d`, затем обязательно снять обе тестовые блокировки. Журнал SSH
должен действительно поступать в jail; для этой конфигурации проверен journald.

`auditd` должен иметь ротацию и ограниченный объём журналов. Не включать тотальное
логирование всех системных вызовов: оно способно быстро заполнить диск.

## Границы защиты

Fail2ban ограничивает перебор, но не исправляет уязвимости приложений и не заменяет
вход по ключам, MFA, проверку прав API, внешние резервные копии и обновления.
До завершения миграции клиентов нельзя молча отключать существующие HTTP API.
Переход на HTTPS и аутентифицированные запросы устройств требует проверки
совместимости установленных приложений.

Источники: [Ubuntu SSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/),
[Docker firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/),
