# Ежедневное резервное копирование

Проверено 18.09.2026 на Ubuntu 26.04 с restic 0.18.1: интеграционный тест
восстановления работающей SQLite в WAL-режиме, обычного файла, второй копии и
отказа без удаления снимков прошёл. На обоих серверах выполнены реальные копии,
полное чтение локальных и удалённых архивов и проверка восстановления всех
SQLite-баз: 12 на сервере панели и 2 на сервере Beszel. Ежедневные таймеры включены.

## Что сохраняется

`fleet-backup.py` использует restic для зашифрованных копий каталогов из
`/etc/fleet-backup/config.json`. Образец `config.example.json` рассчитан на текущий
сервер панели: `/etc`, `/srv`, `/opt`, `/root`, `/home`, `/usr/local` и тома Docker.
На сервере Beszel используются те же каталоги без томов Docker; обязательны
`/opt/beszel/data/data.db` и `auxiliary.db`. Это копия файлов приложений и
конфигураций, а не загрузочный образ диска или снимок всей виртуальной машины.

SQLite определяется по заголовку, а не расширению файла. Для каждой базы создаётся
согласованная копия через SQLite Online Backup API; исходные файлы и журналы
WAL/SHM исключаются из restic. Каждая копия проверяется `integrity_check`.
Пути, владельцы, права и SHA-256 записываются в manifest.json.

После записи архива скрипт проверяет его структуру и восстанавливает все
подготовленные SQLite-копии во временную директорию. Сверяет хеши и снова выполняет
`integrity_check`. При первой копии и затем не реже раза в 7 дней `restic check
--read-data` читает все данные архива. При настроенной второй копии аналогичная
проверка выполняется и для неё. Рабочие базы при проверке не подменяются.

Ограничения: PostgreSQL, MySQL и другие СУБД требуют собственных согласованных
дампов/снимков. Нельзя считать копирование их работающих файлов корректным
резервированием. Файлы вне явно перечисленных каталогов не сохраняются.
Согласованность между разными базами и внешними файлами не является одной общей
транзакцией. Если приложение требует такой согласованности, нужен отдельный
pre-backup hook или остановка приложения на время снимка.

## Развёртывание после проверки сервера

1. Установить restic и Python 3 из репозиториев ОС.
2. Создать `/etc/fleet-backup` и `/var/lib/fleet-backup` с правами root:root 700.
   Пароль restic создать криптографически случайным и сохранить только в
   `/etc/fleet-backup/password` с правами 600. Не выводить его в журнал или Git.
3. Сохранить отдельную защищённую копию пароля вне этих серверов. Без пароля
   восстановление зашифрованных архивов невозможно.
4. Подготовить root-only config.json, сверив roots, исключения и обязательные базы
   `required_sqlite`. Репозиторий и рабочий каталог резервирования должны находиться
   вне всех исходных каталогов. Пароль архива должен быть исключён из источников.
5. Установить скрипт как `/usr/local/sbin/fleet-backup` с правами 750. Установить
   service/timer в `/etc/systemd/system` с правами 644, выполнить daemon-reload.
6. Инициализировать restic-репозиторий с заданным password-file. Повторная
   инициализация существующего архива не нужна.
7. Запустить интеграционный тест, первую реальную копию и проверить status.json,
   журнал, восстановление и свободное место. Только затем включить таймер.

Таймер запускает работу ежедневно в 03:30 по Москве со случайной задержкой до
10 минут. Пропущенный из-за выключения сервера запуск выполняется после загрузки.
Локально сохраняются 14 дневных, 8 недельных и 6 месячных точек; совпадающие
точки не дублируются. Удаление старых точек выполняется только после успешной
проверки новой копии. Неполный снимок (в том числе код restic 3) считается ошибкой.

## Вторая копия без права удаления отправителем

Предпочтительная схема между двумя имеющимися серверами: отдельная учётная запись
получателя без sudo, отдельный ключ, принудительная команда
`rclone serve restic --stdio --append-only` с фиксированным каталогом архива.
Ключ ограничивается исходным IP, запрещаются интерактивный shell, туннели,
перенаправление агента и TTY. Дополнительный публичный порт не нужен: транспорт SSH.
Нельзя использовать взаимный root-доступ серверов для резервирования.

Отправитель может добавлять копии, но не удалять старые через этот интерфейс.
Для такого назначения указать `remote_append_only: true`: скрипт не запускает
удаление на удалённом архиве. Очистка старых точек выполняется отдельно на
получателе с учётом его собственного времени и политики; одних временных меток
снимков от потенциально скомпрометированного отправителя недостаточно.

В текущем развёртывании вторые копии сохраняются без автоматического удаления.
Свободное место необходимо контролировать: заполнение диска приведёт к ошибке
резервирования и может повлиять на приложения. Ограниченное хранение на стороне
получателя или независимое внешнее хранилище требуют отдельной настройки.

Тест удаления выполнен в обоих направлениях на отдельных тестовых снимках:
получен HTTP 403, снимки остались доступны. В restic 0.18.1 команда `forget`
может вернуть код 0 даже при ошибке удаления через этот backend. Проверять нужно
сообщение об отказе и фактическое сохранение снимка, а не только код завершения.

`remote_repository` задаёт backend restic, `remote_options` — дополнительные
аргументы, например `-o rclone.program=ssh ...` и `-o rclone.args=`. Это доверенные
настройки root, а не параметры пользователя панели. Приёмник необходимо проверить
на отказ удаления и перезаписи отдельного тестового снимка до переноса рабочих
данных. Эта схема не защищает от одновременного взлома обоих серверов или потери
обоих дисков. Следующий уровень — отдельное внешнее неизменяемое хранилище.

## Проверка и восстановление

```sh
systemctl status fleet-backup.timer
systemctl list-timers fleet-backup.timer
journalctl -u fleet-backup.service --since yesterday
cat /var/lib/fleet-backup/status.json
python3 test_backup.py
```

`status: ok` выставляется только после всех настроенных проверок. При ошибке
сохраняется время предыдущего успешного запуска. Сам JSON-файл не отправляет
уведомлений: отдельную доставку предупреждений нужно подключить к мониторингу.

Восстанавливать сначала в НОВУЮ директорию, никогда сразу поверх рабочей системы:

```sh
restic -r /var/backups/fleet-restic --password-file /etc/fleet-backup/password snapshots
restic -r /var/backups/fleet-restic --password-file /etc/fleet-backup/password \
  restore SNAPSHOT_ID --target /root/fleet-restore --verify
```

В восстановленной структуре обычные файлы находятся по исходным абсолютным путям
относительно target. Согласованные SQLite-базы находятся в
`var/lib/fleet-backup/staging/sqlite/`, карта — в соседнем `manifest.json`.
Перед заменой рабочей базы остановить соответствующий сервис, сохранить текущую
базу вместе с WAL/SHM, восстановить базу по manifest, владельца и права. Старые
WAL/SHM не должны применяться к восстановленной базе. Затем запустить сервис и
проверить его работу. Автоматического переключения рабочих баз в скрипте нет.

Источники: [restic repositories](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html),
[restic integrity checks](https://restic.readthedocs.io/en/stable/045_working_with_repos.html),
[rclone append-only](https://rclone.org/commands/rclone_serve_restic/).
