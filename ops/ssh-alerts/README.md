# Telegram-алерты об успешном входе root по SSH

Независимая служба для двух серверов. Не подключается к API панели, Beszel или
ByteDepp, не использует PAM hooks и не изменяет sshd_config. Недоступность
Telegram не блокирует вход на сервер.

Отслеживается именно успешная SSH-аутентификация root: интерактивный вход,
удалённая команда, SCP/SFTP или туннель от root. Входы служебных пользователей
`beszel-tunnel` и `fleet-backup` не отправляются. Входы в веб-приложения,
локальную консоль провайдера, `sudo`/`su` и действия внутри уже открытой SSH-сессии
не относятся к этому событию и не отслеживаются. При SSH multiplexing новые
каналы одного аутентифицированного соединения не считаются новым входом.

Сообщение содержит IP сервера, имя root, время события по Москве, фактический
IP и порт источника, метод аутентификации, отпечаток SSH-ключа (если он есть)
и идентификатор события. IP источника может принадлежать VPN/NAT или промежуточному
серверу; страна/город по нему не определяются, внешние GeoIP-сервисы не вызываются.

## Надёжность и границы

- Читается journald для ssh.service/sshd.service. Доверенные поля UID=0 и путь
  исполняемого файла SSH проверяются отдельно от текста сообщения. Строки
  `Accepted key ... found at ...` не считаются отдельным входом.
- Начало работы — с текущего конца журнала, без рассылки старой истории.
  Запись уведомления и продвижение курсора атомарны в SQLite с WAL.
- При рестарте продолжается чтение от сохранённого курсора. Если журнал удалил
  курсор, выполняется повторное чтение с сохранённого времени с дедупликацией.
  Уже удалённые journald события восстановить невозможно.
- Очередь сохраняется на диск, при ошибке Telegram повторяет отправку с задержкой,
  учитывает HTTP 429/retry_after. Успех фиксируется только после подтверждения API.
  Доставка как минимум один раз: если Telegram принял сообщение, но ответ потерян,
  возможен повтор с тем же идентификатором события.
- Очередь не удаляет неотправленные события; записи доставленных хранятся 30 дней.
  При длительной недоступности Telegram нужно контролировать свободное место.
- Root с полным контролем сервера способен остановить службу или изменить журнал.
  Это оповещение, а не защита от действий уже скомпрометированного root.

## Установка

Требуются Python 3 со стандартной библиотекой, systemd/journald, tzdata и CA-сертификаты.
Код устанавливается в `/usr/local/lib/fleet-ssh-alerts`, unit — в
`/etc/systemd/system/fleet-ssh-alerts.service`. Создаётся отдельный системный
пользователь `fleet-ssh-alerts`; право чтения журналов даёт группа systemd-journal.

`/etc/fleet-ssh-alerts/config.json` содержит несекретные параметры из примера
(IP и название меняются для каждого сервера). `/etc/fleet-ssh-alerts/telegram.json`
содержит только `token` и `chatId`. Секретный файл root:root 600 передаётся службе
через systemd LoadCredential. Он не должен попадать в Git, командную строку или
логи. Веб-прокси из переменных окружения для запросов Telegram не используются.

Служба имеет только чтение системных каталогов и запись собственного состояния
в `/var/lib/fleet-ssh-alerts` (700); root-привилегии не требуются.

```sh
python3 test_alerts.py
systemctl daemon-reload
systemctl enable --now fleet-ssh-alerts.service
systemctl status fleet-ssh-alerts.service
journalctl -u fleet-ssh-alerts.service --since '10 minutes ago'
```

После установки проверить реальным НОВЫМ SSH-входом root на каждый сервер,
дождаться подтверждения Telegram и убедиться, что вход служебного пользователя
не создаёт сообщения. Не тестировать сбросом паролей или изменением SSH-доступа.

## Проверено 18.09.2026

Девять автоматических тестов прошли на Ubuntu: IPv4/IPv6, фильтр root, отклонение
неуспешных/служебных/поддельных событий, очередь после повторного открытия,
дедупликация, ответы Telegram и безопасная обработка HTTP 429/сетевых ошибок.
Чтение реального journald проверено от отдельного пользователя службы.

Службы включены на 84.21.173.88 и 94.156.114.97. Telegram API подтвердил доставку
уведомлений о новых root-входах на каждый сервер. Проверен перезапуск службы
с сохранением курсора и очереди, без повторной рассылки старой истории.
Серверы не перезагружались. Используется существующий бот, выбранный владельцем;
передача его секрета между серверами отдельно разрешена владельцем.

Источники: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage),
[journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html).
